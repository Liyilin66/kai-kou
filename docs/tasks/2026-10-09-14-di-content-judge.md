# 任务 14：DI 内容评分可行性验证（答案要点表 + 内容判定 + 稳定性门槛）

- 日期：2026-10-09
- 分支：`lyl`（离线验证，**不改线上**）
- 后续：本任务达标后，另开任务 15 接入线上；不达标则 DI 保持现状，只把发音分改为"未评估"以保持一致

## 为什么先做这一步

RA、RS 有标准原文，内容可以逐词对齐。DI（看图描述）是自由表达，**内容判断离不开"图里到底有什么"**，而现在的题库只有：

- 63 张图（`seeds/di/di-question-catalog.phase1.json`，图片在 `public/di-images/`）
- 每张图只有粗略的 `visualFeatures`（有无趋势、比较、极值、数字）和几个高频词，**没有图中具体内容的答案**

现有评分让 LLM 只看转写文字打分，它既看不到图，也没有答案可对照。所以先验证两件事：能不能为每张图建立可靠的要点答案表；LLM 对照答案表判定内容，结果是否稳定。

## A. 官方规则

在 `docs/ra-scoring-rules.md`（如已改名则用新文件名）增加 DI 一节：查 Pearson Score Guide 中 Describe Image 的评分项和 Content 分档描述，**逐条注明页码**。流利度沿用现有分档判定；发音"本版本未评估"。

## B. 要点答案表 `seeds/di/di-answer-key.json`

1. 用**能看图的模型**为 63 张图逐张生成结构化要点（先确认可用模型：本地已配置的 OpenAI 兼容中转是否支持图片输入；若都不支持，停下来说明，不要用纯文本模型编造图片内容）：

```json
{
  "id": "DI_Q001",
  "answer_key_version": "di-key-0.1",
  "image_type": "bar",
  "points": [
    { "id": "P1", "kind": "topic", "text": "图表主题与对象", "required": true },
    { "id": "P2", "kind": "extreme", "text": "最高值及其类别", "value": "..." },
    { "id": "P3", "kind": "trend", "text": "主要趋势或对比" },
    { "id": "P4", "kind": "number", "text": "关键数字", "value": "..." },
    { "id": "P5", "kind": "conclusion", "text": "可得出的结论" }
  ],
  "generated_by": { "model": "...", "at": "..." },
  "review": { "status": "unreviewed" }
}
```

   - 每张图 4–6 个要点，覆盖：主题、主要元素、关键数字或极值、趋势或对比、结论。
   - 读不清的数字写 `"value": null`，不要猜。
2. **人工抽检**：生成一个本地页面，并排显示图片和要点，让用户检查 8 张（覆盖不同图表类型），每张标记"正确 / 有错 / 读不清"。有错的要点由你修正后，把该图 `review.status` 改为 `reviewed`。这一步预计占用用户 10 分钟。

## C. 内容判定 `backend/speech/di-content-judge.js`

- 输入：答案要点表 + Whisper 转写文本（**不传图片**，保证在线评分便宜且可复现）。
- 模型固定一个（建议 Groq `openai/gpt-oss-120b`，`temperature 0`），**不做主备切换**，避免同一份回答因模型不同而得分不同；调用失败就返回"内容未评分"，不给分。
- 输出：

```json
{
  "covered": [ { "point_id": "P2", "quote": "转写中的原话" } ],
  "missed": ["P4"],
  "inaccurate": [ { "point_id": "P3", "quote": "...", "reason": "说反了趋势" } ],
  "content_band": 3
}
```

- 校验（不通过重试一次，仍不通过 → 内容未评分）：
  - `quote` 必须能在转写中找到（忽略大小写和标点后为子串）；
  - `point_id` 必须存在于答案表；
  - `content_band` 必须与覆盖情况一致——用 A 中整理的官方分档描述，把"覆盖了哪些要点、有无不准确"映射为档位的规则写成代码（项目规则，写进规则页），**模型给出的档位与代码规则不一致时以代码为准并记录**。

## D. 数据与评测

1. 数据来源：线上已有 13 条 DI 练习记录，其中存了录音的，用 Whisper 转写（复用 `eval-run-provider.js` 的方式，缓存不进 Git）。不够 10 条时，用户可在正式网站补录几条 DI（**不强制**，先用现有的跑）。
2. **稳定性**：每条转写判定 5 次，统计档位一致率。
3. **抽查**：随机 5 条，把"覆盖 / 遗漏 / 不准确"的判定结果放进同一个本地页面，让用户判断是否同意（和 B 的抽检合并成一次，总共不超过 15 分钟）。

## 达标门槛（现在定好）

- 要点表：抽检的 8 张图中，**每张最多 1 个要点有错**；
- 稳定性：**≥ 80% 的样本 5 次判定档位完全相同**，其余样本档位差不超过 1；
- 校验通过率：最终（含重试）**≥ 95%**；
- 用户抽查：5 条中**至少 4 条**同意判定结果。

全部达标 → 任务 15 接入线上。不达标 → 如实记录数字，DI 只做"发音改为未评估"这一项一致性修改。**不为凑门槛修改提示词超过一轮。**
